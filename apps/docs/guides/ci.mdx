---
title: "Run evals in CI"
description: "Catch regressions before release"
---

Install `anpord` in your project and commit the lockfile. Name suites `*.eval.ts`
so the action can discover them.

Create an API key with `evals:read` and `evals:write`, then save it as the
`ANPORD_API_KEY` repository secret. Use a dedicated organization for CI.

In that organization, connect the harness under **Settings → Harnesses** and
make it an organization default. API keys cannot use personal connections.
Provider credentials stay in Anpord, not in GitHub or the eval definition.

```yaml
name: Agent evals

on:
  pull_request:
    branches: [main]

permissions:
  contents: read

jobs:
  eval:
    if: >-
      github.actor != 'dependabot[bot]' &&
      github.event.pull_request.head.repo.full_name == github.repository
    runs-on: ubuntu-latest
    timeout-minutes: 30
    steps:
      - uses: actions/checkout@v6
        with:
          ref: ${{ github.event.pull_request.head.sha }}
          persist-credentials: false
      - uses: oven-sh/setup-bun@v2
      - run: bun install --frozen-lockfile
      - uses: charlietlamb/anpord/.github/actions/eval@COMMIT_SHA
        with:
          api-key: ${{ secrets.ANPORD_API_KEY }}
```

Replace `COMMIT_SHA` with a reviewed action commit. The action uses your installed
SDK, not a downloaded CLI. It requires Node 20 or later.

The default `strict` gate requires every expected trial to pass. Failed, void,
missing, and unfinished trials fail the job, including a suite's first run.
Batch links appear in the job summary as soon as submission succeeds.

The dashboard labels these runs **CI** and links back to the exact GitHub
Actions attempt. The CLI reads GitHub's existing environment; no extra setup
or environment overrides are needed.

| Input | Default | Purpose |
| --- | --- | --- |
| `api-key` | Required | Anpord API key |
| `working-directory` | `.` | Project containing the installed SDK |
| `file` | Discover `*.eval.ts` | Run one suite |
| `fail-on` | `failures` | `failures`, `strict`, or `never` |
| `timeout` | `1200` | Seconds to wait per batch |

`failures` fails on any run whose trials did not all pass. `strict` also
requires every expected run and trial to have finished. `never` ignores trial
results. Submission errors, failed batches, and timeouts still fail all gates.

The action's `report` output is the path to a JSON results file. Upload it with
`actions/upload-artifact` and `if: always()` if you want to keep it after the job.

## What runs

A definition that names no source is evaluated against the repository it sits
in. In GitHub Actions, the CLI pins that source to the checked-out commit. The
checkout above tests the PR head, not GitHub's synthetic merge commit.

The action skips fork and Dependabot PRs in this example because they cannot
receive repository secrets. Keep unit tests separate so they still run. Do not
use `pull_request_target` to execute untrusted eval definitions with a secret.

The job itself is the PR check. For an additional check named `anpord`, pass
`GITHUB_TOKEN` in the step environment and grant `checks: write`. Its verdict
matches the selected gate.

Outside the action, the same command is:

```sh
bunx --no-install anpord eval --fail-on failures --timeout 1200 --output results.json
```

## Keep comparisons stable

When testing one change, keep the rest of the [variant](/evals/variants) unchanged so its history stays comparable. Pin fixture repositories to a commit. A harness release stays on the same variant, and each run records the version it used.

Use at least three trials for a gating check. One trial measures an outcome, not repeatability.

## Control the run size

```text
total trials = cases x variants x trials per run
```

Five cases, two variants, and three trials open thirty sandbox sessions. Keep pull request grids small and run larger comparisons on a schedule.

A run holds between 1 and 10 trials. The [API reference](/api-reference/introduction) covers the request limits and what to do when a response is lost.

The CLI records batch IDs before polling and does not retry submissions. A remote
batch continues if CI times out or is cancelled. Open its dashboard link before
starting another.

## What a trial costs

An agent re-sends its whole conversation every turn, so whatever it reads early is paid for again on every turn after it. Pulling a large skill or reading a dependency to work out its API is the usual reason a trial costs ten times its neighbour on the same number of turns.

Tell the agent the interface rather than letting it go looking. A short reference in the workspace is cheaper than the file tree it would otherwise read, and steadier: the trials that explore are the ones whose cost varies most.

Each trial reports its token counts, and the dashboard flags two readings worth acting on -- a context that grew fast, and nothing served from cache. A grid multiplies both: thirty sessions each carrying a large context is thirty times the bill.
