---
title: "Run evals in CI"
description: "Catch regressions before release"
---

Name suites `*.eval.ts` so the same discovery command works locally and in CI.

```yaml
name: Agent evals

on:
  pull_request:

jobs:
  eval:
    runs-on: ubuntu-latest
    timeout-minutes: 30
    permissions:
      contents: read
      checks: write
    steps:
      - uses: actions/checkout@v4
      - uses: oven-sh/setup-bun@v2
      - run: bun install --frozen-lockfile
      - run: bunx anpord eval
        env:
          ANPORD_API_KEY: ${{ secrets.ANPORD_API_KEY }}
          GITHUB_TOKEN: ${{ github.token }}
```

The command waits for the run and exits nonzero when a cell regresses, so the
job fails the request rather than reporting a run nobody reads. Pass
`--fail-on unscored` to also fail a cell that produced no scored trials.

A definition that names no source is evaluated against the repository it sits
in. On a pull request that is the branch the request came from, so the run
measures the change rather than the base branch.

Use a dedicated key with `evals:read` and `evals:write`.

With `GITHUB_TOKEN` present the command also posts one check named `anpord`
on the pull request head, listing every cell with its pass rate, baseline, and
verdict, and linking to the run. The check fails when any cell regressed,
whatever `--fail-on` says; the exit code still follows the gate. A pull
request from a fork gets a read-only token, so the check is skipped with a note
on stderr and the job otherwise runs as before.

## Keep comparisons stable

When testing a prompt change, keep the task, source, setup, verifier, harness, model, and provider unchanged. Those fields form the cell identity. Pin fixture repositories to a commit. A harness release is compared against the existing baseline rather than starting a new one, and a regression names both versions.

Use at least three trials for a gating check. One trial measures an outcome, not repeatability.

## Control the run size

```text
total trials = cases x tasks x trials per cell
```

Five cases, two tasks, and three trials open thirty sandbox sessions. Keep pull request grids small and run larger comparisons on a schedule.

A cell runs between 1 and 10 trials, and one request can contain at most 100 in total. Starting a run is not idempotent. If the response is lost, check recent runs before retrying.

Print the run id before polling. The run continues on the server if the CI job times out.
