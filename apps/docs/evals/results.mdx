`evals.start` returns a run id while trials continue on the server. `startAndWait` runs and resolves once the grid stops:

```ts
const run = await anpord.evals.startAndWait({ cases, prompt, tasks, trials: 3 });
```

To wait on a run you started earlier, pass its id to `evals.wait({ id })`. Both poll `evals.get`, widening the gap as the run goes on, and both take `onProgress`, `signal`, `timeoutMs`, `pollIntervalMs`, and `maxIntervalMs`.

Neither cancels the run. On timeout or abort the grid keeps going, and `evals.get` still reads it.

| Run status | Meaning |
| --- | --- |
| `running` | At least one cell has not finished |
| `finished` | The grid completed, including any void trials |
| `failed` | The grid stopped early; `failure` explains why |

## Cell distribution

```ts
const { passRate, passed, failed, voided, scored, deterministic } =
  run.cells[0].distribution;
```

Pass rate counts only scored trials. When `scored` is zero the pass rate serializes as zero, which is not a result: a later candidate with a baseline reads as `incomparable`.

`deterministic` is true when several scored trials agree on pass or fail and their command counts stay within four. One trial cannot establish it.

## Trial status

| Status | Meaning |
| --- | --- |
| `queued` | Not started |
| `running` | The harness is working |
| `passed` | The verifier passed |
| `failed` | The verifier ran and did not pass |
| `void` | Required evidence is missing |

`voidFields` names the missing evidence where scoring can identify it. Keep void trials out of pass rates in reports and CI: a trial that never ran is not a failure.

## Trajectory

Each trial carries an ordered `trajectory` of commands, messages, tool calls, and file changes:

```ts
for (const event of run.cells[0].trials[0].trajectory) {
  if (event._tag === "command") {
    console.log(event.command, event.exitCode, event.output);
  }
}
```

Trials also record command counts, changed files, model and sandbox time, sandbox id, and token counts where the harness reports them. Output and tool payloads cap at 4,000 characters, and truncation is marked.

Read the distribution first, then compare a passing and a failing trajectory from the same cell. The pass rate says what happened; the command counts say how the attempts differed.

## Validation evidence

Each trial's `validations` holds the code checks, judges, and command verifier that scored it:

```ts
for (const validation of run.cells[0].trials[0].validations) {
  console.log(validation.name, validation.status, validation.durationMs);
  console.log(validation.input, validation.output, validation.error);
}
```

Code checks record their return value, context arguments and results, logs, and exceptions. Judges record the prompt, raw response, provider metadata, and parsed judgment. Command verifiers record the command, stdout, stderr, and exit code.

`failed` is a check that completed and did not pass. `error` is one that could not finish. `skipped` is one that never ran. Earlier checks stay visible when a later one crashes, and a run that predates capture cannot recover it.

Each validator gets a 64,000-character budget, single values cap at 16,000, and at most 64 calls or log entries are kept. Truncation affects the stored evidence, never the score.

Inputs and logs can contain your data. `captureValidation: false` on `defineEval` keeps verdicts and timing but stores no payloads, separately from `captureSource`. Credentials and model reasoning are never collected, but a validator that prints a secret will store it.

## Run origin

Each run records a `trigger`: Dashboard, CLI, CI, API, or MCP, which trials inherit. The CLI and MCP set it; direct API calls default to API. Other automation can pass its own:

```ts
trigger: { source: "ci", url: "https://ci.example/run/123" }
```

This describes the caller. It grants nothing and verifies nothing. Resuming keeps the original trigger, running again records the new one, and older runs show Unknown.
