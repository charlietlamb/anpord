## Run origin

Each run records a `trigger`: Dashboard, CLI, CI, API, or MCP. It appears in the
run list, details, and history. Trials inherit their run's origin.

The CLI and MCP set it automatically. Direct API calls default to API. Other
automation can supply `trigger: { source: "ci", url: "https://ci.example/run/123" }`
when starting or rerunning an eval. This metadata describes the caller; it
does not grant permissions or verify a CI provider's identity.

Resuming preserves the original trigger. Running again records the new caller.
Older runs show Unknown.

`evals.start` returns a run id while trials continue on the server. `startAndWait` starts a run and resolves once it stops:

```ts
const run = await anpord.evals.startAndWait({ cases, prompt, tasks, trials: 3 });
```

To wait on a run you started earlier, pass its id:

```ts
const run = await anpord.evals.wait({ id });
```

Both poll `evals.get`, widening the gap between requests as the run goes on. Both accept:

| Option | Default | Purpose |
| --- | --- | --- |
| `onProgress` | None | Called with the run after every poll |
| `signal` | None | Stop waiting when an `AbortSignal` fires |
| `timeoutMs` | 1 hour | Give up waiting and throw `EvalTimeout` |
| `pollIntervalMs` | 2000 | Gap before the first re-check |
| `maxIntervalMs` | 10000 | Ceiling the gap grows to |

Neither cancels the run. On timeout or abort the grid keeps going on the server, and `evals.get` still reads it.

| Run status | Meaning |
| --- | --- |
| `running` | At least one cell has not finished |
| `finished` | The grid completed, including any void trials |
| `failed` | The grid stopped early; `failure` explains why |

## Cell distribution

```ts
const result = run.cells[0]?.distribution;

console.log({
  passRate: result?.passRate,
  passed: result?.passed,
  failed: result?.failed,
  voided: result?.voided,
  scored: result?.scored,
  deterministic: result?.deterministic,
});
```

Pass rate uses scored trials as its denominator. If `scored` is zero, the serialized pass rate is zero, but there is no scored result. A later unscored candidate with a baseline is `incomparable`.

`deterministic` is true when multiple scored trials agree on pass or fail and their command counts stay within four. One scored trial cannot establish determinism.

## Trial status

| Status | Meaning |
| --- | --- |
| `queued` | Reserved for work that has not started |
| `running` | The harness is working |
| `passed` | The verifier passed |
| `failed` | The verifier ran and did not pass |
| `void` | Required evidence is missing |
| `exceeded` | Reserved for a runtime or resource limit |

`voidFields` lists missing evidence when scoring can identify it. Keep void trials separate from failures in reports and CI.

## Trajectory

The detail view includes the prompt and a **Validation** panel with captured source files. Select a file to read or copy its original contents. These are compile-time snapshots, not the current files in your repository. See [source capture](/evals/cases#validate).

Each trial includes an ordered `trajectory` of commands, messages, tool calls, and file changes:

```ts
for (const event of run.cells[0]?.trials[0]?.trajectory ?? []) {
  if (event._tag === "command") {
    console.log(event.command, event.exitCode, event.output);
  }
}
```

Trial metadata also includes command counts, changed files, model and sandbox time, sandbox id, and token counts when the harness reports them. Command output and tool payloads are capped at 4,000 characters, with truncation marked explicitly.

Read the distribution first, then compare passing and failing trajectories from the same cell. Pass rate summarizes outcomes. Command counts show how attempts differed.

## Validation evidence

Each trial's `validations` contains the individual code checks, judges, or command verifier. The dashboard shows these under **Validation results**, alongside the original source files.

```ts
for (const validation of run.cells[0]?.trials[0]?.validations ?? []) {
  console.log(validation.name, validation.status, validation.durationMs);
  console.log(validation.input, validation.output, validation.error);
  console.log(validation.calls, validation.logs);
}
```

Code checks record their return value, context method arguments and results, console logs, and exceptions. Judges record the request body or harness prompt, raw response text, provider metadata when available, and parsed judgment. Command verifiers record their command, stdout, stderr, and exit code. This uses the same execution path for CI, CLI, API, MCP, and dashboard runs.

`failed` means a completed check did not pass. `error` means it could not finish reliably. `skipped` means it did not run. Earlier completed checks remain visible if a later check crashes. Historical runs cannot recover evidence that was never captured.

Values carry `state`, `format`, `text`, and `truncated`. Capture is limited to 16,000 characters per value, 64,000 per validator, and 64 calls or log entries. Truncation affects stored evidence, not scoring. Unavailable evidence is never presented as an empty result.

Inputs, results, and logs can contain your data. Set `captureValidation: false` on `defineEval` to disable payload capture for code checks and judges while retaining their verdicts and timing. This is separate from `captureSource`. Authorization headers, credentials, and private model reasoning are not collected by the capture layer; do not print secrets from your own validators. Worker logs include validation status transitions and run, cell, trial, and validator identifiers, not payloads.
