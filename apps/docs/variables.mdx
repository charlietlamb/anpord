---
title: "Variables"
description: "Values filled in at runtime, checked at build time"
---

A prompt can leave gaps for values the caller supplies:

```
You are a support agent for {{product}}. The customer is {{name}}.
```

Pass them to `get` and the content comes back filled in:

```ts
const prompt = await anpord.prompts.get({
  id: "support-reply",
  variables: { product: "Anpord", name: "Charlie" },
});
```

## The typo that fails the build

Prompts live outside your codebase, so a renamed variable would normally break in production rather than in review. Anpord moves that failure to compile time.

```bash
npx anpord generate
```

This writes `anpord-env.d.ts`, describing which variables each prompt takes:

```ts
// Generated by `anpord generate`. Do not edit.
import "anpord";

declare module "anpord" {
  interface AnpordPromptVariables {
    "support-reply": { "product": string; "name": string };
  }
}
```

Now `tsc` rejects a name the prompt does not use:

```ts
await anpord.prompts.get({
  id: "support-reply",
  variables: { product: "Anpord", nmae: "Charlie" },
});
// Object literal may only specify known properties,
// and 'nmae' does not exist in type '{ product: string; name: string }'.
```

It also rejects a name the prompt does use and the caller forgot. Both are build errors, not failed requests.

Commit the generated file and run the command again whenever a prompt gains or loses a variable.

## Prompts with no variables yet

A prompt that declared no variables when the file was written is read as unknown rather than as empty. Someone adding the first variable in the dashboard does not break a build that never passed one.

Once a prompt names variables, callers are held to that shape, so regenerate after adding another.

## Without generation

`generate` is optional. Skip it and `variables` accepts any object, substituting what it can. The gaps stay in the content when a value is missing, which is visible in the model's output rather than in your logs.
